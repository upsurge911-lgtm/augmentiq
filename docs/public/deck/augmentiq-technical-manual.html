Component 1 — the product

Obsidian plugin: the server and the memory

One install. No Docker, no separate process, no daemon. Enabling the plugin starts an MCP server inside Obsidian and creates the memory store in the vault.

  • Embedded streamable-HTTP MCP server on 127.0.0.1:3710
  • Bearer token generated on first enable; copy from ribbon or settings
  • Read-only mode enforced server-side, not by convention
  • Vault deletes go to system trash — never hard-deleted
  • Records stored as Context Records; audit log is SHA-256 chained

Component 1 — data model

What a memory actually is

// .augmentiq/memories.jsonl — one record per line
{
  "schema_version": "1.0",
  "id": "augmentiq:9c1f…",
  "timestamp": "2026-10-24T14:00:00Z",
  "scope": "individual",
  "source": "chat:session:2026-10-24",
  "content": "User prefers concise answers.",
  "tags": ["preference","communication"],
  "classification": "internal",
  "audit_ref": "augmentiq-tl:4e8b…"
}

Bi-temporal by design

Two timestamps, never conflated: timestamp is when the fact happened; recorded_at is when it was stored. Legacy ingest keeps the original event time.

Classified, not just stored

Every record carries public / internal / confidential / restricted. A PII pattern match forces at least confidential.

Audit is not optional

Each write appends a timeline entry: audit_hash = sha256(entry), chained onto previous_hash. That is what makes the trail tamper-evident rather than merely present.

Component 2 — the adapter

OpenClaw plugin: native tools, no shelling out

Without it, an OpenClaw agent reaches AugmentiQ through mcporter or raw HTTP. With it, the same six operations are first-class native tools with typed schemas and friendly errors.

  • Built with defineToolPlugin from the OpenClaw plugin SDK
  • Proxies each call to the vault server over loopback HTTP
  • Exact contract tool names preserved, so skill flows work unchanged
  • Typed errors: server down, 401, not configured
// plugins.entries.augmentiq.config
{
  "token": "<from Obsidian settings>",
  "baseUrl": "http://127.0.0.1:3710/mcp"
}
Config accepts a literal string only. SecretRefs resolve for model and provider config, not for plugin config objects. A ref here fails validation with “must be string”.
Component 3 — the playbook

Skill: what to do, in what order, with confirmation

The skill carries no code. It carries judgement: when to remember, when to ask, in what order to act, and which of 26 subcommands maps to which flow.

Structure

Portable package

SKILL.md under 5k tokens, plus 22 reference docs and assets. Progressive disclosure: only the body loads until a task needs detail.

Reach

7 hosts, one package

Hermes, OpenClaw, Claude Desktop, Claude Code, Codex, Cursor, nanobot — and any of 30+ agentskills.io-compliant hosts.

Restraint

5 immutable principles

Per-action confirmation · host keeps authority · reversible · confirm before destructive · audit everything.

The principles are the constitution. Every flow and every command derives from them — which is why the skill can safely run on an agent you do not fully trust with your vault.

What gets written

Observation, conclusion, preference, instruction, summary — each with scope, tags, and importance 1–5. Quality over quantity: 3–5 per session is the target, not 30.

What never gets written

Secrets, API keys, passwords, sensitive PII. The skill instructs refusal; classification rules upgrade anything PII-adjacent before it reaches the store.

Deployment

What the customer does

# 1 — the vault gives you the memory
Obsidian → Settings → Community plugins → AugmentiQ → Enable
        → copy the bearer token from the ribbon

# 2 — the host gets the tools
openclaw plugins install clawhub:upsurge/augmentiq
        → paste the token

# 3 — the host gets the judgement
cp -r AugmentiQ/ ~/.openclaw/workspace/skills/augmentiq/
# other hosts: same folder, that host's skills directory
Time

Under 5 minutes

Three steps. No Docker, no daemon, no external service.

Privileges

Obsidian desktop; the server binds loopback exclusively.

Security model

Why this is safe to point at a real vault

PropertyMechanism
Network exposureServer binds 127.0.0.1 only. No remote listener, no cloud relay.
AuthenticationAuto-generated bearer token, constant-time compared on every request.
Data at restPlain files in .augmentiq/ inside your vault — inspectable, backupable, yours.
Tamper evidenceSHA-256 chained audit; verification is a served operation, not a promise.
Destructive actionsConfirm required; vault deletes go to trash; pre-destroy export offered.
Read-only modeServer rejects every write with -32002 when enabled.
Honest caveat. The bearer token is stored in plaintext in the host config (the same place other local credentials live). The transport is loopback HTTP, not TLS. Both are acceptable for a single-user local machine; neither is a substitute for OS-level access control.

Limits and next

What v0.1 deliberately does not do

Out of scope now

  • Local embeddings — recall is lexical in v0.1
  • Mobile Obsidian
  • Org-tier roles and multi-user memory
  • Compliance packs (GDPR / SOC2 / HIPAA / ISO)
  • Enterprise Docker backend

Sequence to launch

  • Sustained dogfood on a real vault
  • ClawHub publish + Obsidian directory submission
  • Install docs per host, tested from clean state
  • v1.1: embeddings behind a flag
  • Then enterprise backend

The product is one plugin. Everything else is an adapter that makes it reachable. Keep that hierarchy in view and the roadmap stays honest.
